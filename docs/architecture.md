# Архитектура системы

## Логическая схема

```
        ┌────────────────────┐         REST API (HTTPS)        ┌──────────────────────┐
        │  Клиент (React)     │  ────────────────────────────► │  Сервер (FastAPI)     │
        │  доказывающий       │   /params /register            │  проверяющий          │
        │                     │   /auth/start|commit|respond   │                       │
        │  • генерация s, v   │ ◄────────────────────────────  │  • проверка y²≡x·vᵉ   │
        │  • x = r² mod n     │      запрос e, токен            │  • управление сессиями│
        │  • y = r·sᵉ mod n   │                                 │  • журнал событий     │
        └────────────────────┘                                 └──────────┬───────────┘
                                                                          │ SQLAlchemy
        ┌────────────────────┐         REST API (Bearer)                  ▼
        │  Админ-панель       │  ────────────────────────────►  ┌──────────────────────┐
        │  (React)            │   /admin/overview|users|...     │  БД: MySQL / SQLite   │
        │  • сводка, журналы  │ ◄────────────────────────────   │  5 таблиц             │
        └────────────────────┘                                 └──────────────────────┘
```

- **Клиент** играет роль доказывающего: генерирует ключевую пару, вычисляет
  обязательства и отклики. Секрет `s` хранится только на клиенте.
- **Сервер** играет роль проверяющего: обрабатывает регистрацию, формирует
  запросы, проверяет отклики и управляет сессиями.
- **База данных** хранит учётные записи, верификаторы и журнал событий.
- **Веб-интерфейс администратора** отображает данные администратору.

## Слои бэкенда

```
backend/app/
├── crypto/fiatshamir.py   # самописная модульная арифметика и шаги протокола
├── models.py              # ORM-модели (5 таблиц)
├── schemas.py             # Pydantic-схемы запросов/ответов
├── services/
│   ├── trusted_center.py  # генерация и хранение модуля n
│   ├── registration.py    # регистрация пользователя
│   ├── auth.py            # конечный автомат сессии (проверяющий)
│   ├── admin.py           # сводная статистика
│   └── events.py          # запись событий и итогов попыток
├── routers/               # HTTP-маршруты (public, auth, admin)
├── security.py            # авторизация администратора
└── main.py                # сборка приложения FastAPI
```

## Схема базы данных (5 таблиц)

### `users` — учётные записи
| Поле | Тип | Описание |
|------|-----|----------|
| id | int PK | идентификатор |
| username | str unique | имя пользователя |
| display_name | str? | отображаемое имя |
| is_active | bool | активность учётной записи |
| consecutive_failures | int | счётчик последовательных неудач (порог ошибок) |
| locked_until | datetime? | время снятия временной блокировки |
| created_at | datetime | дата создания |

### `verifiers` — открытые верификаторы и параметры протокола
| Поле | Тип | Описание |
|------|-----|----------|
| id | int PK | идентификатор |
| user_id | FK users | владелец |
| modulus_n | text | модуль `n` (строка) |
| verifier_v | text | верификатор `v = s² mod n` |
| rounds | int | число раундов |
| algorithm | str | имя протокола (`fiat-shamir`) |

Секрет `s` **не хранится** — в таблице только открытое значение `v`.

### `auth_sessions` — состояние текущих сессий
| Поле | Тип | Описание |
|------|-----|----------|
| session_id | str unique | идентификатор сессии (UUID) |
| user_id | FK users | пользователь |
| status | enum | `awaiting_commitment` / `awaiting_response` / `success` / `failed` / `expired` |
| mode | str | `interactive` (пошаговый) или `non-interactive` (один пакет) |
| total_rounds / current_round | int | прогресс по раундам |
| integrity_errors | int | сколько раз раунд переотправлен из-за искажения в канале |
| commitment_x / challenge_e | text/int | текущее обязательство и запрос |
| token | str? | сессионный токен при успехе |
| client_ip, user_agent | str? | метаданные |
| created_at, expires_at, completed_at | datetime | временные метки |

### `auth_results` — история попыток входа
| Поле | Тип | Описание |
|------|-----|----------|
| id | int PK | идентификатор |
| user_id / username | FK / str | пользователь |
| session_id | str? | сессия |
| outcome | enum | `success` / `failure` / `timeout` (три исхода из статьи) |
| rounds_completed / total_rounds | int | сколько раундов пройдено |
| detail, client_ip | str? | пояснение и адрес |
| created_at | datetime | время |

### `events` — события для администратора
| Поле | Тип | Описание |
|------|-----|----------|
| id | int PK | идентификатор |
| type | enum | `registration` / `login_success` / `login_failure` / `session_timeout` / `suspicious` |
| severity | enum | `info` / `warning` / `critical` |
| user_id, session_id | FK / str | контекст |
| message | str | текст события |
| created_at | datetime | время |

### `auth_round_logs` — подробный журнал раундов (расширение для аудита)
Дополнительная таблица сверх пяти базовых: хранит для каждого раунда обязательство
`x`, запрос `e`, отклик `y`, обе части контрольного равенства (`lhs = y² mod n`,
`rhs = x·vᵉ mod n`) и итог `verified`. Используется кнопкой «Подробнее» в админ-
панели для пошагового просмотра вычислений и проверок конкретной сессии.

| Поле | Тип | Описание |
|------|-----|----------|
| session_id | str | сессия |
| round_index | int | номер раунда (с 1) |
| commitment_x / challenge_e / response_y | text/int/text | величины раунда |
| lhs / rhs | text | левая и правая части равенства |
| verified | bool | пройдена ли проверка |

## Три исхода попытки входа

1. **success** — все раунды пройдены, выдаётся сессионный токен;
2. **failure** — ошибка проверки отклика (неверный ввод или попытка самозванца);
3. **timeout** — сессия не завершена в отведённый срок (`ZEROFS_SESSION_TTL`).

Раздельный учёт исходов помогает отличать признаки подбора и
несанкционированного доступа от обычных сетевых сбоев и незавершённых сессий.

## Порог ошибок (защита от подбора)

После `ZEROFS_MAX_FAILURES` (по умолчанию 3) **последовательных** неудач подряд
учётная запись временно блокируется на `ZEROFS_LOCKOUT_SECONDS` (300 с). Счётчик
ведётся в `users.consecutive_failures`, время снятия — в `users.locked_until`;
успешный вход сбрасывает счётчик, блокировка снимается автоматически по истечении
времени. Засчитываются только реальные отказы (`failure`) — таймауты и искажения
канала к порогу не относятся, так как это технические сбои, а не подбор.

## Устойчивость к техническим сбоям канала

Внутри математики протокола ошибаться нельзя: единственный неверный отклик уже
доказывает незнание секрета, а ослабление проверки разрушило бы стойкость `2⁻ᵗ`.
Технические сбои отделяются от криптографических двумя средствами:

1. **Контроль целостности.** К числам `x` и `y` прикладывается контрольная сумма
   `SHA-256`. Несовпадение на сервере означает искажение в канале → раунд
   переотправляется без штрафа (поле `auth_sessions.integrity_errors` считает такие
   повторы). Корректное число с несошедшимся равенством — это настоящий отказ.

2. **Неинтерактивный вариант** (`mode = non-interactive`). Запросы выводятся из
   хэша всех обязательств: `eᵢ = бит i от SHA-256(n│v│x₁│…│x_t)`. Доказательство
   передаётся одним пакетом, поэтому обрыв связи лечится повторной отправкой без
   потери стойкости. Так как `eᵢ` зависят от всех `x`, обязательства нельзя
   подобрать задним числом — свойство стойкости сохраняется.

Хэширование выполняется стандартной `SHA-256` (требование эвристики Фиата–Шамира);
модульная арифметика протокола остаётся самописной.

## Ограничения учебной реализации

- самописные модули криптографии **не сертифицированы**;
- требуется защищённый канал (TLS) против повторного воспроизведения и MITM;
- секрет на клиенте хранится в `localStorage` (в продакшене — шифровать);
- необходимы ограничение частоты попыток и доверенная генерация модуля.

## Направления развития

Схема Фейге–Фиата–Шамира с вектором секретов; варианты на эллиптических кривых;
неинтерактивное преобразование Фиата–Шамира и интеграция с токенами доступа;
интеграция с SSO/IAM, экспорт журналов и учёт постквантовых угроз.
