# Протокол Фиата–Шамира с нулевым разглашением

## Идея

Доказательство с нулевым разглашением позволяет одной стороне (доказывающему)
убедить другую (проверяющего) в истинности утверждения, не раскрывая никакой
дополнительной информации, кроме самого факта истинности. В контексте
аутентификации пользователь доказывает **знание секрета**, не передавая секрет
по сети и не размещая его на сервере.

Протокол опирается на три свойства:

- **полнота** — честный доказывающий всегда убеждает честного проверяющего;
- **корректность** — нечестный доказывающий не может обмануть проверяющего иначе
  как с пренебрежимо малой вероятностью;
- **нулевое разглашение** — проверяющий не узнаёт ничего о самом секрете.

## Математическая основа

Стойкость схемы основана на сложности извлечения квадратного корня по модулю
большого составного числа `n`, факторизация которого неизвестна.

1. Доверенный центр выбирает `n = p · q`, где `p`, `q` — большие простые. Число
   `n` общедоступно, а `p`, `q` держатся в секрете (в прототипе после генерации
   `n` множители не сохраняются).
2. Доказывающий выбирает секрет `s`, взаимно простой с `n`, и публикует
   **верификатор** `v = s² mod n`.

## Раунд протокола

Каждый раунд состоит из трёх сообщений «обязательство — запрос — отклик»:

| Шаг | Сторона | Действие |
|-----|---------|----------|
| 1. Обязательство | доказывающий | выбирает случайное `r`, отправляет `x = r² mod n` |
| 2. Запрос | проверяющий | выбирает случайный бит `e ∈ {0, 1}` |
| 3. Отклик | доказывающий | отправляет `y = r · sᵉ mod n` |
| 4. Проверка | проверяющий | принимает раунд, если `y² ≡ x · vᵉ (mod n)` |

### Почему проверка верна для честного доказывающего

```
y² = (r · sᵉ)² = r² · s²ᵉ = r² · (s²)ᵉ = x · vᵉ  (mod n)
```

### Почему самозванец проваливается

Не зная `s`, доказывающий должен заранее угадать бит `e`:

- если он готовится к `e = 0`, то не сможет ответить на `e = 1` (нужен `s`);
- если он готовится к `e = 1` (например, фиксирует `x = r²/v`), то не сможет
  ответить на `e = 0`.

Поскольку `e` выбирается проверяющим случайно **после** получения `x`, вероятность
успешного обмана в одном раунде равна `1/2`.

## Усиление гарантии

После `t` независимых раундов вероятность обмана не превышает `2⁻ᵗ`. Число раундов
задаётся параметром `ZEROFS_ROUNDS` (по умолчанию 20, то есть вероятность ≤ 2⁻²⁰ ≈
10⁻⁶). Функция `cheating_probability(t)` возвращает эту оценку.

## Неинтерактивный вариант (эвристика Фиата–Шамира)

Интерактивный обмен «вопрос–ответ» чувствителен к обрывам связи: потеря одного
сообщения прерывает сессию. Эвристика Фиата–Шамира убирает интерактивность,
заменяя случайные биты проверяющего значением хэш-функции от обязательств:

```
eᵢ = бит i числа  SHA-256(n │ v │ x₁ │ x₂ │ … │ x_t)
```

Доказывающий вычисляет все `t` обязательств `xᵢ = rᵢ² mod n`, сам выводит запросы
`eᵢ` по формуле выше, считает отклики `yᵢ = rᵢ · sᵉ mod n` и отправляет всё
**одним пакетом**. Проверяющий повторяет вычисление `eᵢ` из тех же обязательств и
проверяет каждое равенство `yᵢ² ≡ xᵢ · vᵉ (mod n)`.

Стойкость сохраняется: так как каждый `eᵢ` зависит сразу от всех обязательств,
доказывающий не может подобрать `xᵢ` под удобные запросы (это потребовало бы
обращения хэш-функции). Вероятность обмана по-прежнему `≤ 2⁻ᵗ`. Практическая
выгода — устойчивость к сбоям: обрыв связи лечится повторной отправкой того же
пакета без потери безопасности. Реализация: `derive_challenges` (сервер и тесты),
`deriveChallenges` (клиент), эндпоинт `POST /api/auth/verify-proof`.

## Контроль целостности канала

Чтобы отличить искажение данных в канале от математически неверного отклика, к
каждому передаваемому числу прикладывается контрольная сумма `SHA-256`. Если на
стороне получателя пересчитанный хэш не совпал — значение повреждено при передаче
(технический сбой), и раунд переотправляется без штрафа. Если число корректно, но
равенство `y² ≡ x · vᵉ` не выполняется — это настоящий отказ. Реализация:
`value_checksum` (сервер), `valueChecksum` (клиент); поле `checksum` в `/auth/commit`
и `/auth/respond`.

> Обе надстройки используют стандартную хэш-функцию `SHA-256` — это требование
> самой эвристики Фиата–Шамира. Модульная арифметика протокола остаётся самописной.

## Соответствие коду

- `backend/app/crypto/fiatshamir.py` — серверная математика, шаги протокола,
  `value_checksum`, `derive_challenges`;
- `client/src/crypto.js` — те же шаги на стороне клиента (BigInt) и SHA-256;
- `backend/app/services/auth.py` — конечный автомат сессии и неинтерактивная
  проверка (роль проверяющего).

## Развитие

- **схема Фейге–Фиата–Шамира** с вектором секретов — меньше раундов;
- **варианты на эллиптических кривых** — короче ключи;
- **zk-SNARK / zk-STARK** — компактные неинтерактивные доказательства, где
  неинтерактивное преобразование Фиата–Шамира является базовым приёмом.
